    04 / LOCKS

    Two customers race. The database decides.

    Both requests can reach the service simultaneously. The first transaction to acquire the row lock proceeds; the second waits, then re-reads the committed status and receives 409 SEAT_UNAVAILABLE.

    This simulation alternates the winner to emphasize that thread timing is nondeterministic while the invariant is deterministic.

    Seat selection

    Ordered acquisition

    Requested show-seat IDs are queried in ascending ID order. Every transaction asks for multi-seat locks in the same order, reducing deadlock cycles.

    Hold conversion

    Hold then inventory

    Confirmation locks the hold row, verifies ownership and TTL, then locks all rows carrying that hold ID before payment and conversion.

    Discounts

    Redemption counter lock

    A discount row is locked before checking validity and remaining redemptions, preventing concurrent requests from exceeding the configured maximum.

    Cancellation

    Booking lock

    The booking row is locked before checking CONFIRMED status, calculating a refund, and releasing its seats, preventing duplicate cancellation.

    Outbox

    Delivery lock

    The dispatcher locks up to 25 due PENDING events so two application instances cannot send the same row concurrently.

    Secondary guard

    Optimistic version

    show_seat.version gives Hibernate an additional stale-write check. Pessimistic locking remains the primary allocation mechanism.

    05 / ATOMICITY

    What commits together, and what happens when it fails

    Each write use case is a Spring transaction. Managed entity changes are flushed together at commit; an exception rolls the unit of work back.

    HOLD TRANSACTION

    Inventory and hold agree

    Expired inventory is reclaimed, requested seat rows are locked, a seat_hold plus items are inserted, and each seat moves to HELD with the same expiry timestamp.

    CONFIRMATION TRANSACTION

    Payment evidence, booking, seats, and event agree

    The active hold and seats are locked, the optional discount is locked, payment is captured, then booking, items, payment record, BOOKED seats, CONVERTED hold, redemption count, and outbox event commit together.

    CANCELLATION TRANSACTION

    Refund decision and released inventory agree

    The booking is locked, the applicable time tier selects a percentage, the payment adapter refunds when needed, then cancellation, refund audit row, AVAILABLE seats, payment status, and outbox event commit together.

    OUTBOX REQUIREMENT

    Notification intent cannot escape its parent transaction

    OutboxService.enqueue uses Propagation.MANDATORY. Calling it outside a transaction fails immediately, preventing accidental non-atomic event writes.

    Production tradeoff

    Payment runs while locks are held

    The current mock is instant. A real network gateway could extend lock duration. A production evolution would introduce PENDING_PAYMENT plus webhook reconciliation.

    Production tradeoff

    No SKIP LOCKED dispatch

    Outbox workers use pessimistic locks without skip-locked partitioning. Multiple instances remain correct but may block each other instead of maximizing throughput.

    Database backstop

    Unique keys close retry races

    (customer_id, idempotency_key), hold-to-booking uniqueness, event dedupe keys, and one payment/refund per booking protect invariants below application code.

    06 / ASYNC

    Background work stays outside customer latency

    Schedulers maintain availability and delivery. The booking request persists intent; a worker handles notification side effects afterward.

    Every 30 seconds

    Hold expiry sweep

    Locks active holds whose expiry is due, marks them EXPIRED, finds HELD seats with due timestamps, and releases them to AVAILABLE. Creating a new hold also performs lazy cleanup first.

    Every 2 seconds

    Outbox dispatch

    Fetches a locked page of 25 due PENDING events. Success marks SENT. Failure delays the event by 30 seconds; the fifth failed attempt marks it FAILED.

    Every 5 minutes

    Show reminders

    Finds confirmed bookings starting 55 to 65 minutes ahead, batches customer lookup, and inserts a deduplicated SHOW_REMINDER event.

    REQUEST PATH

    Persist notification intent

    BOOKING_CONFIRMED or BOOKING_CANCELLED is serialized to JSON and inserted as PENDING with a unique dedupe key.

    AFTER COMMIT

    Claim and deliver

    The dispatcher locks eligible rows and sends through the NotificationSender port. The local adapter logs the payload; email or SMS can replace it.

    DELIVERY SEMANTICS

    At-least-once intent, idempotent row creation

    Dedupe keys prevent duplicate event rows. A real sender should also be idempotent because a process crash between external delivery and SENT persistence can still cause redelivery.

    09 / PROOF

    The guarantees are exercised, not only documented

    The Spring integration suite boots the real context with Flyway, Hibernate, H2, security, repositories, services, and transaction management.

    Pricing

    Tier plus weekend snapshots

    Verifies regular and premium seat prices and the minimum display price for a showing.

    Scheduling

    Overlap rejection

    Attempts a conflicting showing on the same screen and expects SCREEN_SCHEDULE_CONFLICT.

    Lifecycle

    Hold, confirm, retry

    Confirms once, retries with the same key, and verifies one booking event and BOOKED inventory.

    Rollback

    Decline then retry

    Forces a payment decline, then confirms successfully from the same hold with no partial write.

    Refund

    Discount and cancellation

    Checks discounted total, time-tiered refund, released seat, and both outbox events.

    Threads

    One winner race

    Starts two executor threads behind one latch and asserts exactly one hold plus one seat conflict.
